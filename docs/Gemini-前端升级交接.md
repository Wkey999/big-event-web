## 当前设计的思路

1. 内容优先：读者应先看到值得阅读的标题、内容主题和来源，而不是大量操作按钮、统计面板和管理表格。
2. 前后台分开：社区使用共享导航和阅读布局；分类维护、资讯审核等管理功能保留独立后台。
3. 稳定的阅读层级：标题、摘要、来源、作者及互动信息有清楚的主次，避免每个元素都抢注意力。
4. AI 作为发现内容的辅助能力：保留明显的 AI 搜索入口、真实引用来源及配置入口，不让 AI 模块压过社区主体。
5. 克制的视觉：当前使用浅灰绿页面、白色内容区、低饱和深绿品牌色、细边框和适度圆角，减少装饰带来的阅读负担。这是现有选择，不是必须保留的约束。
6. 功能渐进加载：富文本编辑器和游戏在使用时加载，不让首页承担全部功能的资源成本。

目前首页使用左侧频道、中间卡片信息流、右侧辅助内容。顶部有发现、AI 搜索、小游戏、站内搜索、创作和个人入口。页面最小宽度当前为 1100px，主要面向 PC。

## 建议重点改善的问题

- 资讯经常没有封面，当前卡片会用大号标题生成占位封面，正文区域又重复标题，导致重复和空耗。可以设计无图链接卡片、文字卡片、有图卡片等真实内容形态，不必强行为所有内容配大图。
- 当前瀑布流通过估算高度分栏，卡片比例还有按 ID 分配的变化。重新评估是否适合以文字为主的资讯，优先考虑阅读顺序、稳定性和扫描效率。
- 精简占空间的口号、提示和侧栏装饰，把空间留给真实内容。不要新增没有数据支撑的热榜、在线人数、趋势图等。
- 统一字号、行高、栅格、间距、卡片密度、按钮层级、焦点和加载状态。长中文标题、英文原始标题、缺图和加载失败都需要自然呈现。
- 全局样式较集中且部分规则排得很紧，可以整理成可维护的样式结构。不要为了改视觉迁移整套技术栈。
- 不必一次重做全站。优先完成首页、共享导航和文章卡片，再统一搜索与阅读页，然后处理 AI、个人资料和创作页，最后协调后台样式。

## 可以自由调整与必须保留的边界

可以调整：配色、字体、布局、卡片形式、信息密度、导航呈现、装饰文案、侧栏内容取舍、组件组织方式。允许提出比当前瀑布流更适合资讯阅读的方案。

需要保持或验证：

- 使用真实 API，不用 mock 数据替换已接通的数据。分类来自接口，不把分类 ID、数量和排序写死；关注分类启用状态。
- 现有 `/`、`/search`、`/ask`、`/games`、`/read/:id`、`/creator`、`/profile` 及 `/admin/articles`、`/admin/categories`、`/admin/feeds` 路由可访问，登录和管理员权限仍生效。
- 搜索条件通过 URL 保留，刷新、后退和分页不丢失。创作页 `compose`、`edit` 参数与文章所有权判断保持有效。
- 请求统一走 `src/utils/request.js`，前端基地址为 `/api`；开发代理转给后端并去掉 `/api`。不要擅自给后端接口再加一层前缀。
- 文章 HTML 继续消毒处理；来源链接和外部资讯来源提示真实存在，不把聚合资讯伪装成本站原创。
- 点赞、收藏、浏览与曝光等记录保持现有语义，避免因组件重复挂载或视觉预加载产生重复写入。编辑文章不要误用会增加浏览量的详情请求。
- AI 保留平台体验与自填 API 的选择、明显配置入口和真实参考来源。个人 API 凭据目前只保存在当前标签页内存，刷新或退出清除，不改存 localStorage/sessionStorage，不写入源码或日志。不要自动改用平台密钥，也不要为视觉验收发起付费模型调用。
- 当前 AI 是单次问答/检索界面，不应凭空宣传多轮、流式、向量数据库或已训练推荐模型等未实现能力。
- 头像选择保留四个入口：DeepSeek、GPT、查看更多、上传图片；保留预览、保存和恢复等行为，避免给用户上传图片套用预设人物的偏移。
- 游戏只在用户点击开始后加载，保留暂停、继续、退出清理与消息来源检查；不为重做社区界面改写游戏包。
- 采集后台保留原始来源、中文标题编辑、人工审核与官方白名单状态。最新 GitHub 官方博客、选定 DeepSeek/千问官方仓库的发布策略以现有后端为准，不在前端绕过审核或伪造成功。
- 保留路由、编辑器和游戏的按需加载，以及 Element Plus 现有按需引入。不要修改生成的 `dist`、依赖缓存或游戏打包产物来替代源代码修改。

推荐和最新信息流的分页策略不同；重排卡片时先读 `useFeed.js`，保留去重、过期请求防护和曝光观察。不要为演示效果添加假的无限滚动。
